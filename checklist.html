Architecture review · 12 September 2026

A promising beta; safe team ownership is still to be built

The simple static pages, shared styling, source notes and automated deployment are useful foundations. The missing layer is a publishing system that prevents routine mistakes, gives editors clear feedback and makes recovery easy. Marketing should own content and approval; a named technical owner should own the safeguards.

What the repository shows

  • 23 HTML files, shared CSS/JavaScript and direct deployment from main; no CMS or pre-deployment content test stage.
  • A local scan of HTML href/src targets and fragments found no missing local files or named anchors, but one placeholder Annual Report link on Our Funders. This does not test external destinations, CSS URLs, srcset, live server behaviour or inbox delivery.
  • Internal HTML pages are included in deployment. Password protection is commented out by prior request; search exclusion does not make material private.
  • Navigation and footer markup are copied across pages. Search metadata, image processing, link checks and approvals need repeatable defaults rather than editor memory.

Priorities for this beta

  1. Before public launch: clear disclosure and consent, fix contact/action destinations, preserve donation and old URLs, enforce publish checks and prove recovery.
  2. Before team ownership: trial guided editing versus a structured CMS, share content records, practise preview/approval/undo and appoint owners.
  3. After launch: use monitoring, search and enquiry evidence to guide improvements. Defer optional features explicitly rather than treating every Open row as a launch blocker.

Evidence limits: this review inspected the local HTML, JavaScript, server/deploy configuration and project notes, and checked local HTML links. Earlier visual, contrast and device results remain historical claims, not newly rerun tests. Live hosting, branch protections, payments, permissions and source-document approvals were not verified. New rows are requirements, not implemented features. For rows 1–13, use Launch scope review to assign priorities before declaring readiness.

Reference guidance: Google: AI features and your website; Google: site moves; W3C: tabs; W3C: accordions. Recommendations in the new sections are proposed acceptance criteria for GoSports; applicable legal and financial requirements need the responsible owners' review.

14 · Building it with Claude Code

What worked, what to watch

This site has been built and maintained through Claude Code by a non-engineering team. That's a fair test of the approach.

Where it's strong

  • Turning source documents into structured pages quickly: 21 pages from two documents.
  • Systematic checks a human wouldn't do by hand: contrast, overflow, broken images, tap targets across every page at two widths in minutes.
  • Consistent fixes across many files at once, with the reasoning recorded in commit messages.
  • Plumbing that used to need a developer: deploys, caching, security headers, image processing.

Where the team must stay in charge

  • Facts. Contact emails were invented to make buttons work, and a heading said "five pillars" over four cards. Every name, number and claim needs a human source check before publishing.
  • Judgement calls. What to disclose (Performance Institute), how to describe SAPA, which headline: these are leadership decisions, and Claude should surface them, not make them.
  • Taste. The design is consistent and competent. One pass by a brand designer before launch is still worth it.
  • Devices. Headless-browser checks are not the same as a phone in someone's hand.

What a static site can't do alone

  • Forms, donations and newsletters need a third-party service. Pick them early (see Giving and enquiries).
  • There is no CMS. Prove whether guided AI editing with protected templates or a structured CMS works for this team before choosing the long-term editing approach. Headcount alone does not settle that decision.
  • Search over the site's own content isn't available without a service.

A workflow that works for a marketing team

  1. Describe the change in plain words, with the source for any fact.
  2. Claude edits, then shows the result at phone and desktop width.
  3. A second person checks names and numbers.
  4. Publish the approved version only after required checks pass. Today main auto-deploys; the enforced approval and preview gates below still need implementation.
  5. Close the item on the handover page in the same change.
  6. Check the deployed version and key journeys; show the team the result and recovery action. Run automatic checks on every publish.
